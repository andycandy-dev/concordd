* Overview

IPC system for ~concordd~ to enable external clients (primarily Emacs) to interact with Discord.

** Implementation Status: ✅ v1.0 COMPLETE

The v1.0 implementation is complete and functional. All core features are working:
- ✅ Unix socket server with JSON-RPC 2.0
- ✅ Discord gateway connection with state management
- ✅ Complete CRUD API (12 methods total)
- ✅ Real-time push notifications (7 event types)
- ✅ Message caching for performance
- ✅ Message pagination
- ✅ Edit/delete own messages
- ✅ Graceful shutdown
- ✅ Guild member and role metadata
- ✅ Full-featured Emacs client (discord.el)
- ✅ Mention rendering support
- ✅ Evil mode compatibility

** Design Principles
- Daemon is standalone, explicitly controlled
- System manages lifecycle (systemd, etc.)
- Push-based event model (daemon → clients)
- Simple JSON-RPC 2.0 over Unix domain socket
- Client-side caching and rendering
- Minimal viable implementation first

* Transport Protocol

** Socket
- Unix domain socket (file-based)
- Default: ~/tmp/concordd.sock~
- Configurable via ~--socket-path~ flag
- Permissions: 0600 (owner only)

** Message Format
- JSON-RPC 2.0 specification
- Text-based (UTF-8)
- Line-delimited (each message ends with \n)

*** Request (Client → Daemon)
#+begin_src json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "sendMessage",
  "params": {
    "channelId": "123456789",
    "content": "Hello, world!"
  }
}
#+end_src

*** Response (Daemon → Client)
#+begin_src json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "messageId": "987654321",
    "timestamp": "2025-12-27T12:00:00Z"
  }
}
#+end_src

*** Error Response
#+begin_src json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32600,
    "message": "Invalid channel ID"
  }
}
#+end_src

*** Notification (Daemon → Client, no response expected)
#+begin_src json
{

  "method": "messageCreated",
  "params": {
    "channelId": "123456789",

** Event Flow

*** Client Request
1. Client sends JSON-RPC request
2. Server parses and validates
3. Handler executes (e.g., sendMessage)
4. Discord API called
5. Response sent to client

*** Discord Event
1. Gateway event received (e.g., MESSAGE_CREATE)
2. Cache updated
3. Event transformed to IPC notification
4. Broadcast to all connected clients

* Security Considerations

** Socket Permissions
- Socket file: mode 0600 (owner read/write only)
- Prevents other users from connecting

** Authentication
- No authentication in MVP (same-user trust model)
- Future: challenge-response or shared secret

** Rate Limiting
- Respect Discord API rate limits
- Queue messages if needed
- Notify clients of rate limit status

** Data Privacy
- Token never exposed via IPC
- Cached messages stored in memory only (MVP)
- Consider encryption for future disk cache

* Performance Characteristics

** Message Caching

The daemon implements intelligent message caching:

*** First Request (Cold Cache)
- ~5-30 seconds depending on channel size and network latency
- Fetches from Discord API
- Populates cache
- Returns data

*** Subsequent Requests (Warm Cache)
- ~Instant (< 100ms)
- Served from memory cache
- No network calls

*** Real-time Updates
- New messages automatically update cache
- Push notifications sent to all connected clients
- Cache stays in sync with Discord state

** Benefits Over Standalone Tools

| Feature | Standalone CLI | Daemon + IPC |
|---------+----------------+--------------|
| Authentication | Every call | Once |
| Message fetch | 5-30s each time | Instant (cached) |
| Real-time updates | Manual polling | Push notifications |
| Resource usage | High (repeated connections) | Low (single connection) |
| Latency | Network round-trip | Local IPC |

* Known Issues & Limitations

** Current Limitations

1. **First message fetch is slow**: This is expected - Discord API needs to be queried initially
2. **No persistence**: Message cache is in-memory only, lost on restart
3. **Single token**: Daemon runs as one Discord user
4. **No authentication**: Any local process can connect to the socket (mitigated by file permissions)
5. **No edit/delete**: Can't edit or delete sent messages
6. **Basic rendering**: No embeds, code blocks, or rich formatting
7. **No attachment support**: Can't upload or properly display files
